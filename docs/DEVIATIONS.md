# Sprint 1 Deviations and Deferred Scope

This document records known implementation differences, process gaps, and scope decisions at the end of Sprint 1. The planned resolutions below are forward-looking actions; they do not imply that the work is already complete.

| Item | Reason | Current impact | Planned resolution |
|---|---|---|---|
| Patient records are persisted to a file, while doctor, appointment, and user-account data are held in memory. | Sprint 1 prioritized patient-data persistence and the selected feature set; durable storage for the other entities was not included in the initial implementation scope. | Doctor, appointment, and account changes are lost when the application exits. Patient records remain available through the current file store. | In a later sprint, add durable repositories for doctors, appointments, and accounts, with appropriate validation and migration/back-up considerations. |
| GitHub Actions was added after the initial Sprint 1 feature integration and is being completed through a separate PR. | The team integrated the feature work before the CI workflow was available on `main`. | The initial integration PR was not automatically validated by the repository workflow. Later PRs can use the workflow once it is merged and passing. | Merge the workflow PR after owner review, then require successful build and test checks for subsequent changes. |
| Initial Sprint 1 features were consolidated into one integration PR instead of individual teammate-raised PRs. | The team chose a single integration PR to bring the Sprint 1 implementation together. | Individual teammate PR, review, and merge evidence is missing for that initial integration, so the repository history does not show the intended collaboration process for those changes. | Use separate teammate-owned PRs for remaining work; have the repository owner review and merge them, with CI checks passing. |
| Admission, room, medical-record, billing, reporting, and backup features are not implemented. | These features were outside the requirements selected for Sprint 1 and are deferred to later sprints. | Those workflows are not available in the current application. This does not change the completion status of the selected Sprint 1 requirements. | Add the deferred features to a future sprint backlog, estimate and prioritize them, then implement and verify them against the relevant SRS requirements. |
| The application uses a console interface. | The SRS permits a console-based application for the current project. | Users interact through terminal menus; there is no graphical interface. This is a documented design choice, not a deviation from the SRS. | Keep the console interface unless a later requirement or approved design change calls for a graphical interface. |
